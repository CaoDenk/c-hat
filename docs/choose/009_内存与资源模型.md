## 1. 背景

C^ 文档同时描述了 RAII、`defer`、`late`、`new/delete`、引用、移动和异常展开。  
当前实现只落地了其中一部分，且 `defer` 作用域、自动析构、移动语义仍与文档不一致。

需要明确资源模型的主语义，避免后续每次实现都重新解释设计文档。

---

## 2. 决策

### 2.1 `defer` 是块级作用域

- `defer` 绑定到最近一层 `{}`。
- 支持 `defer expr;` 与 `defer { ... }`。
- 同一作用域内多个 defer 按 LIFO 执行。
- 循环体内 defer 每次迭代注册、每次迭代结束执行。
- `return` / `throw` / `break` / `continue` 退出作用域时执行对应 cleanup。
- defer 与析构函数使用同一个 cleanup 栈，按注册/构造顺序统一 LIFO。
- defer 在异常展开中再次抛异常时 `terminate`。

### 2.2 RAII 作为默认资源管理

- 栈上类值和 `late` 成功构造的对象在作用域退出时自动析构。
- 堆对象继续使用显式 `new/delete`。
- 析构函数不应抛异常；清理路径中抛异常统一 `terminate`。
- 析构函数调用顺序为逆声明顺序，且与 defer 统一按 cleanup 栈 LIFO 执行。

### 2.3 `late` 语义

- `late T x;` 只预留存储，不构造对象。
- 第一次赋值执行构造，后续赋值执行正常赋值。
- 只有成功构造的对象才参与析构。
- 使用未初始化 `late` 是编译错误。
- `late` 与 RVO/NRVO 的交互后续单独评审。

### 2.4 `new/delete` 与数组元素生命周期

- `new T(...)` 调用构造函数。
- `new T[n]` 对非平凡类型逐元素默认构造；构造失败时逆序析构已构造元素。
- `delete p` 调用析构函数后释放内存。
- `delete` 释放指针或 owning slice；空指针 delete 为 no-op。
- `delete[]` 作为兼容/底层形式保留，但 canonical 写法是 `delete slice`。
- 切片拷贝是浅拷贝，不转移所有权；所有权由创建者负责。

### 2.5 引用与移动

- `T&` 是可变借用，调用点必须 `f(&x)`。
- `T!&` 是只读借用，允许 `f(x)`。
- 引用 ABI 先固定为指针。
- `~` 表示所有权转移，不改变底层表示。
- 移动后源对象进入“已移动”状态，禁止使用；析构时按空资源处理。
- `self~` 表示移动接收者，方法体不能在移动后继续使用 `self`。
- 第一阶段只支持显式移动，不做隐式移动优化。

### 2.6 异常展开

- 短期继续使用 `setjmp/longjmp`。
- 清理模型按逐帧 cleanup 设计，避免未来推倒。
- 当前作用域 cleanup 执行 defer + 析构，然后向外传播。
- catch 捕获后，try 内对象已按展开规则清理。
- 清理过程中抛异常统一 `terminate`。
- 结构体/类异常 payload 单独设计，不长期依赖 64 位字。

## 3. 备选方案

### 方案 A：函数级 defer，不做自动析构

优点：实现最小。  
缺点：与 C^ 的 RAII/late 文档冲突，资源管理模型不完整。

结论：不选。

### 方案 B：完整 RAII（栈值、late、数组元素、异常展开）

优点：语言模型统一。  
缺点：实现量最大，牵涉类型系统、异常、数组、移动。

结论：作为长期目标，不作为 v1 全量实现。

### 方案 C：块级 defer + 栈上/late RAII + 堆内存显式管理（推荐）

优点：兑现 C^ 的核心资源模型，同时控制实现复杂度。  
缺点：仍需要 scope cleanup、late 状态跟踪、异常展开。

结论：选 C。

## 4. 对现有代码的影响

主要涉及：

- `src/parser/Parser.cpp`：`defer {}`、`~`、引用语法
- `src/semantic/SemanticAnalyzer.*`：作用域、构造状态、生命周期、移动检查
- `src/llvm/LLVMCodeGenerator.*`：scope cleanup、析构调用、异常展开、数组元素生命周期
- `src/ast/`：defer 复合语句、移动/引用节点
- `tests/defer/`、`tests/exception/`、`tests/late/`、`tests/reference/`、`tests/new_delete/`
- `docs/spec/C^ 语言内存管理规范.md`
- `docs/spec/C^ 语言错误处理规范.md`
- `docs/design/defer设计.md`
- `docs/design/构造析构设计.md`
- `docs/design/late设计.md`

行为变化：

- 函数级 defer 的现有代码可能改变执行时机；
- 自动析构会让部分“忘记 delete”的代码不再泄漏；
- 移动后源对象使用会被拒绝；
- 异常展开可能触发析构，改变可观察行为；
- 文档中未实现的 RAII 承诺需要删除或标记 experimental。

## 5. 迁移计划

### Phase 0：冻结语义与文档

- 明确 `defer` 是块级；
- 明确自动析构范围；
- 明确 `late`、引用、移动是否属于 v1；
- 把未实现项从“已支持”文档中移出；
- 增加负向测试。

### Phase 1：块级 defer

- parser 支持 `defer { ... }`；
- codegen 使用作用域栈，而不是函数级 vector；
- 每个作用域注册 cleanup region；
- 循环内 defer 每次迭代注册/执行；
- return/throw/break/continue 按作用域边界执行；
- 保留运行时 flag 防止未执行分支。

### Phase 2：栈上/late 自动析构

- 识别有析构函数的局部对象；
- 记录构造状态；
- 正常作用域退出逆序析构；
- return/throw 路径析构；
- `late` 只在成功构造后析构；
- 加入 RVO/移动的最小规则。

### Phase 3：异常展开整合

- 当前函数 cleanup 执行 defer + 析构；
- 中间函数帧逐层清理；
- catch 捕获后 try 内对象已清理；
- 清理过程中抛异常 `terminate`；
- 明确 `setjmp/longjmp` 下的对象状态。

### Phase 4：数组元素生命周期

- `new T[n]` 逐元素构造；
- 构造失败逆序析构；
- `delete[]` 逐元素析构；
- 切片/数组拷贝规则；
- 数组字面量构造规则。

### Phase 5：引用与移动

- 完成可变引用 codegen；
- 引用返回/生命周期检查；
- `~` 移动语义；
- `self~`；
- 移动后源对象状态。

- 文档中 `defer` 的作用域与实现一致；

- 循环内 defer 行为有明确测试；
- 栈上/late 对象析构有端到端测试；
- 异常展开时 defer/析构顺序有测试；
- `new T[n]` / `delete[]` 对非平凡类型有测试；
- 可变引用有端到端测试；
- 移动 `~` 有语义测试（若进入 v1）；
