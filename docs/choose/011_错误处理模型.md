## 1. 背景

C^ 文档里同时存在三种错误处理路径：

- `T?`：可能没有值
- `Result<T, E>`：可恢复、可预期错误
- `try/catch/throw`：运行时异常

当前实现主要覆盖：

- nullable 比较与部分 `?` 传播
- `Result` 的 parser/semantic 基础
- `try/catch/throw` 通过 `setjmp/longjmp`
- `catch (T e)` 按类型标签精确匹配
- `throw` / 裸 `throw;` 重新抛出
- 含 `defer` 的函数安装清理帧
- 64 位异常 payload

但还没有：

- `Result` / `?` 的完整 codegen
- 异常对象的类型化 payload
- 基类/接口 catch 匹配
- 自动析构展开
- 零开销表驱动异常

因此需要先明确错误模型的分工和异常 ABI。

---

## 2. 决策

### 2.1 三层错误模型

C^ 使用三层错误处理，各层职责明确：

1. **`T?`（optional）**
   - 只表达“可能没有值”；
   - 不携带错误原因；
   - 用于缺值、查找失败、可空引用等场景。

2. **`Result<T, E>`**
   - 表达可恢复、可预期的错误；
   - 调用点必须显式处理或传播；
   - `?` 用于错误传播；
   - 推荐业务代码主要使用。

3. **`try/catch/throw`**
   - 用于不可恢复、违反不变量、资源失败、编程错误；
   - 不作为普通控制流；
   - 通过异常展开执行清理。

规则：

- 可预期错误优先 `Result<T, E>`；
- 缺值语义优先 `T?`；
- 异常只用于真正异常的控制流；
- `?` 在 nullable 和 `Result` 上语义尽量同构，但类型系统必须区分。

### 2.2 异常表示

异常不再用 64 位字硬塞 payload。

异常对象建议表示为：

```text
ExceptionObject {
  typeinfo*  type;      // 运行时类型信息
  void*      payload;   // 标量值或堆对象地址
  ...
}
```

- 标量异常可以按值存储在 payload；
- 类/结构体异常建议按指针或 owning object 存储；
- `throw e` 对非平凡类型构造异常对象；
- `throw;` 重新抛出当前异常，保留原始类型信息；
- `catch` 的类型匹配基于 `typeinfo`，而不是 64 位 tag；
- `catch (...)` 接受所有异常。

### 2.3 catch 匹配规则

- 按书写顺序尝试 catch；
- `catch (T e)` 对值类型按值捕获；
- `catch (T& e)` / `catch (T!& e)` 对引用类型按引用捕获；
- `catch (Base e)` 可以匹配派生类；
- `catch (Interface e)` 可以匹配实现类；
- `catch (...)` 接受所有异常；
- 未匹配的异常继续向外传播；
- catch 参数只在 catch 体内部可见，不泄漏到后续语句。

### 2.4 异常展开与清理

异常展开时，按作用域从内到外执行 cleanup：

1. 当前作用域的 defer（LIFO）
2. 当前作用域已构造对象的析构函数（LIFO）
3. 向外层传播
4. 中间函数帧逐层清理
5. 到达匹配的 catch
6. catch 体执行

规则：

- catch 捕获前，try 内对象已按展开规则清理；
- 清理过程中抛异常 → `terminate`；
- defer/析构不应抛异常；如果抛异常，统一 `terminate`；
- 未捕获异常最终 `terminate`；
- 裸 `throw;` 保留原始异常对象与类型信息。

### 2.5 `Result<T, E>` 与 `?`

- `Result<T, E>` 是值类型；
- `Ok(T)` / `Err(E)` 构造；
- `?` 在 `Result` 上：如果是 `Err`，立即返回当前函数；
- `?` 在 `T?` 上：如果是 `null`，立即返回当前函数；
- `?` 只能在返回 `Result` / 可空类型或兼容类型时使用；
- `Result` 的错误类型 `E` 必须可复制或可移动；
- `Result` 不应隐式转换为 `T`。

### 2.6 nullable 语义

- `T?` 表示可能没有值；
- `null` 是唯一缺值；
- `!` 强制解包，失败时抛异常或 terminate（需明确）；
- `?` 传播缺值；
- 只读可空 `T!?` 与可变可空 `T?` 的转换遵循只读单向规则；
- 指针可空 `T^?` 与值可空 `T?` 的表示可不同，但语义一致。

### 2.7 已确认补充决策

1. **三层模型都属于 v1 语言规范。**
   - `T?`、`Result<T, E>`、异常都是语言层能力。
   - `Result` codegen 可分阶段实现，但语义不标记 experimental。
   - 可预期错误优先 `Result`，缺值优先 `T?`，异常只用于真正异常。

2. **catch 捕获规则。**
   - 标量类型按值捕获：`catch (int e)`。
   - class/struct 按引用捕获：`catch (T& e)` / `catch (T!& e)`。
   - `catch (T e)` 对非平凡类型不推荐，避免切片/拷贝。
   - `catch (Base e)` 匹配派生类。
   - `catch (Interface e)` 匹配实现类。

3. **基类/接口匹配。**
   - 基于 typeinfo，不使用 64 位 tag。
   - 按 catch 书写顺序匹配。
   - 未匹配继续向外传播。
   - `catch (...)` 接受所有异常。

4. **`!` 强制解包失败。**
   - 触发运行时 panic/terminate。
   - 可恢复缺值使用 `?`、`match` 或显式检查。
   - 不把 `!` 作为异常控制流。

5. **异常对象存储。**
   - 由运行时管理，不要求用户堆分配。
   - 具体是栈槽、堆对象还是异常池由运行时 ABI 决定。
   - 非平凡异常对象由运行时复制/移动并负责析构。
   - 长期 ABI 不依赖 64 位字。

6. **`Result<T, E>` 的 E。**
   - 要求可复制或可移动。
   - v1 先支持 trivially copyable / 简单类型。
   - 非平凡 E 后续扩展。

7. **`?` 链式传播。**
   - 允许链式 `?`。
   - 每层必须类型兼容。
   - `Result` 与 nullable 的 `?` 语义同构，但类型系统区分。

8. **`Result` codegen。**
   - 属于 v1，但实现分阶段。
   - 先支持 `Ok`/`Err`、`?` 传播、简单 E。
   - 复杂 E / 移动后续扩展。

9. **异常展开机制。**
   - 短期继续 `setjmp/longjmp`。
   - cleanup API 独立于异常机制。
   - 零开销表驱动后续实现。

10. **defer/析构抛异常。**
    - 统一 `terminate`。
    - 清理路径不允许继续抛出。

## 3. 备选方案

### 方案 A：只保留异常

优点：实现最小。  
缺点：与文档中的 `Result` / nullable 设计冲突，业务错误处理不清晰。

结论：不选。

### 方案 B：只保留 `Result<T, E>`

优点：可恢复错误显式。  
缺点：无法表达不可恢复异常，`try/catch` 文档和现有实现作废。

结论：不选。

### 方案 C：三层模型（推荐）

优点：分工明确，兼容现有设计。  
缺点：需要定义三者边界和转换规则。

结论：选 C。

## 4. ABI / payload 设计

异常对象建议至少包含：

```text
ExceptionObject {
  typeinfo* type;
  void*     payload;
  ...
}
```

- 标量：payload 可存储标量值或其地址；
- 类/结构体：payload 存储对象地址；
- catch by value：对平凡类型复制；
- catch by reference：不复制，直接绑定 payload；
- `catch (...)` 通过 `typeinfo` 接受所有异常；
- 重新抛出保留 `typeinfo` 与 payload。

`setjmp/longjmp` 阶段可以先用全局异常槽 + 类型标签过渡，但长期 ABI 不应依赖 64 位字。

## 6. 迁移计划

### Phase 0：冻结语义与文档

- 明确三层错误模型的推荐路径；
- 明确 `?` 在 nullable 和 `Result` 上的规则；
- 明确 catch by value / by reference；
- 明确异常 payload 设计；
- 更新文档，移除“catch 不做类型匹配”的旧说法。

### Phase 1：异常对象与类型匹配

- 引入 `ExceptionObject`；
- `throw` 构造异常对象；
- `catch` 基于 typeinfo 匹配；
- 支持基类/接口匹配；
- `throw;` 保留原始异常。

### Phase 2：展开与清理

- 当前函数 cleanup 执行 defer + 析构；
- 中间函数帧逐层清理；
- catch 捕获后 try 内对象已清理；
- 清理异常 terminate。

### Phase 3：`Result<T, E>` 与 `?`

- `Result` 值类型 codegen；
- `Ok` / `Err` 构造；
- `?` 传播；
- `Result` 与 nullable 的 `?` 语义对齐。

### Phase 4：零开销异常

- 设计表驱动 ABI；
- vtable/typeinfo 集成；
- 将 setjmp/longjmp 替换为 invoke/landingpad；
- 保留 cleanup API。

## 7. 开放问题确认结果

1. 三层模型都属于 v1 语言规范；Result codegen 分阶段。
2. 标量按值捕获；class/struct 按引用捕获。
3. `catch (Base e)` 匹配派生类；接口同理。
4. `!` 失败触发 panic/terminate，不作为异常控制流。
5. 异常对象由运行时管理，不要求用户堆分配。
6. `Result` 的 E 要求可复制/可移动；v1 先支持简单类型。
7. `?` 允许链式传播。
8. `Result` codegen 属于 v1，但分阶段实现。
9. 短期 setjmp/longjmp，cleanup API 独立设计。
10. defer/析构抛异常统一 terminate。

---

## 8. 验收标准

- `catch (T e)` 按类型匹配；
- `catch (Base e)` 匹配派生类；
- `throw;` 保留原始异常类型；
- 异常展开执行 defer + 析构；
- 清理过程中异常 terminate；
- `Result<T, E>` / `?` 有端到端测试；
- nullable `?` 有端到端测试；
- 异常 payload 不再依赖 64 位字；
- 文档中异常限制与实现一致。
