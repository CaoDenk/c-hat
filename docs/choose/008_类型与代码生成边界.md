# 008：类型与代码生成边界

**状态**：草案  
**日期**：2026-11-01  
**范围**：AST、语义类型、LLVM 类型降低、变量/表达式类型、重载、泛型、ABI  
**相关文档**：

---

## 1. 背景

当前 C^ 编译器存在三层类型信息：

1. AST 语法类型：`ast::Type`
2. 语义类型：`types::Type`
3. LLVM 类型：`llvm::Type`

其中 semantic 类型没有统一附着到表达式上，codegen 会根据 AST 形状或 LLVM 值反推类型。这已经导致：

- `var x = a[0] + a[1]` 被推断成 `int`
- `double` 条件误用 `ICmp`
- 数组字面量运行时用切片表示，但语义类型是固定数组
- 指针 pointee 类型通过旁路表补充
- `isReadonlyType`、`generateTypeExpr` 等语义信息在 codegen 中丢失

因此需要明确边界：**类型检查由 semantic 负责，codegen 只消费已确定类型。**

---

## 2. 决策

### 2.1 表达式类型存放在独立 SemanticModel

AST 保持纯语法，不直接保存 `types::Type`。

SemanticModel 保存：

```cpp
std::unordered_map<const ast::Expression *, std::shared_ptr<types::Type>> exprTypes;
std::unordered_map<const ast::Declaration *, std::shared_ptr<types::Type>> declTypes;
std::unordered_map<const ast::CallExpr *, std::string> resolvedCalls;
```

codegen 通过 `SemanticModel` 读取类型。

### 2.2 codegen 禁止类型回退

codegen 不允许：

- 根据初始化器形状推断变量类型；
- 根据 LLVM 值猜数组/切片/元组/类；
- 缺失类型时默认使用 `int32`；
- 按 LLVM 类型拼接 mangled name 作为备用重载解析。

缺失类型时，codegen 必须报错。

### 2.3 统一 TypeLowering

所有 `types::Type -> llvm::Type` 转换统一经过 `TypeLowering`。

要求：

- 数组、切片、元组、类、结构体、引用、只读、可空、函数类型都有明确规则；
- 不允许业务分支临时拼接 LLVM 类型；
- 未知类型返回 `nullptr` 并报错；
- 只读信息在 LLVM 层可擦除，但擦除规则必须固定并测试。

### 2.4 变量类型由 SemanticModel 决定

- 有显式类型：使用 semantic 类型；
- 无显式类型：使用初始化器表达式的 semantic 类型；
- `new T[n]` 的返回类型由 semantic 决定为 `T[]`；
- 数组/元组/切片字面量的语法糖类型由 semantic 决定。

### 2.5 重载与 mangling 由 semantic 决定

- `CallExpr::resolvedMangledName` 是唯一调用目标；
- codegen 不再按 LLVM 实参类型拼接 mangled name；
- 泛型单态化后的名称由 semantic 生成。

---

## 3. 备选方案

### 方案 A：AST 直接保存语义类型

优点：查找直接。  
缺点：AST 与 semantic types 耦合，泛型克隆、序列化、测试更复杂。

结论：不选。

### 方案 B：保留 codegen 类型猜测

优点：短期兼容现有代码。  
缺点：错误被隐藏，后续在 IR 层崩溃，难定位。

结论：不选。

### 方案 C：SemanticModel + TypeLowering（推荐）

优点：分层清晰，便于测试、dump、ABI 收敛。  
缺点：需要为所有表达式记录类型，迁移成本高。

结论：选 C。

---

## 4. 对现有代码的影响

主要涉及：

- `src/semantic/SemanticAnalyzer.*`
- `src/semantic/SemanticModel.h`
- `src/llvm/LLVMCodeGenerator.*`
- `src/types/*`
- `src/main.cpp`
- `tests/integration/IntegrationTest.cpp`

行为变化：

- 一些目前“靠 codegen 猜对”的代码会被拒绝；
- 一些目前能通过但类型不一致的代码会暴露为 semantic 错误；
- `int32` 回退删除后，未实现类型会明确报错；
- `namedValuePointeeTypes_` 等旁路表逐步删除。

---

## 5. 迁移计划

### Phase 0：冻结与记录

- SemanticModel 记录所有表达式类型；
- codegen 接收 SemanticModel；
- 不改变现有生成逻辑。

### Phase 1：移除变量类型推断

- `generateVariableDecl` 改为读取 SemanticModel；
- 删除字面量/调用/成员/二元表达式分支的 varType 推断；
- 保留显式类型转换；
- 跑全量测试，修复 semantic 漏记录。

### Phase 2：统一 TypeLowering

- 抽出纯类型降低逻辑；
- 移除 `generateType` 中的 `int32` 默认回退；
- 明确数组/切片/元组/引用/只读/可空规则；
- 删除 `namedValuePointeeTypes_`。

### Phase 3：ABI 与值语义

- 冻结数组/切片/元组/类的 LLVM 表示；
- 处理函数参数/返回值 ABI；
- 处理泛型单态化后的类型一致性。

### Phase 4：只读 / 引用 / 移动

- 明确只读擦除规则；
- 完成可变引用 codegen；
- 定义 `~` 移动语义与类型关系。

---

## 6. 验收标准

- 所有 `ast::Expression` 在 semantic 后都有类型记录；
- `generateVariableDecl` 不再有初始化器形状推断；
- `generateType` 不再对未知类型返回 `int32`；
- `generateMemberExpr` / `generateSubscriptExpr` 不再依赖 LLVM 值猜类型；
- 函数调用只使用 semantic 解析结果；
- 新增类型一致性测试：
  - double 表达式变量
  - 数组/切片/元组/类字段
  - 指针/引用/只读
  - 泛型单态化
  - 重载调用
- 文档中的类型状态与实现一致。

## 7. 待确认问题

1. SemanticModel 是否由 codegen 以指针接收，还是作为 generate 参数？
2. `generateType` 是否完全替换为 `TypeLowering`，还是先保留 AST Type 入口？
3. `varType` 推断删除后，`var` 无初始化器的类型如何处理？
4. 类型缓存是否以 `types::Type` 为 key？
5. 只读类型在 LLVM 层是否完全擦除？
6. 引用在 LLVM 层是否固定为指针？
