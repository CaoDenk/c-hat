## 1. 背景

C^ 需要同时满足两个目标：

1. 编译器默认提供可用的标准库；
2. 语言核心不能依赖标准库，标准库可以被替换或完全缺失。

尤其异常：如果异常只能抛标准库类型，那么没有标准库就不能抛异常，这是不可接受的。  
因此异常必须是语言机制，而不是标准库机制。

---

## 2. 决策

### 2.1 四层结构

C^ 分为四层：

1. **语言核心**：编译器必须独立支持
2. **编译器运行时**：`libc_hat_rt` 或等价运行时
3. **默认标准库**：`std.*`
4. **平台 / libc / OS**

### 2.2 语言核心

语言核心不依赖标准库，包括：

- 基础类型
- 变量、函数、控制流
- 数组 / 切片 / 元组
- 指针 / 引用
- struct / class / interface
- `defer`
- `try/catch/throw`
- RAII / 析构
- `new/delete` 的分配器钩子
- `literalview`
- 泛型 / concept

### 2.3 编译器运行时

建议有独立运行时：

```text
libc_hat_rt
```

负责：

- 异常展开
- 类型信息 / typeinfo
- cleanup 调用
- `terminate` / `abort` / panic 钩子
- 默认分配器钩子
- 可能的栈展开/帧信息

运行时不是标准库。  
没有标准库时，异常仍然可以工作；只是没有 `std.string`、`std.io`、`std.collections` 等。

### 2.4 默认标准库

编译器默认提供：

```text
std.core
std.mem
std.string
std.text
std.io
std.math
std.test
```

标准库是默认实现，不是语言核心。

### 2.5 标准库可替换、可缺失

- `--stdlib-path <path>`：指向自定义标准库
- `--no-stdlib`：禁用默认标准库
- 默认不自动 import 标准库；用户显式 `import std...`
- 自定义标准库可以使用自己的命名空间，也可以替换 `std.*`
- 编译器不能硬编码 `std.string`、`std.error`、`std.io` 等名字
- 无标准库时，语言核心和异常仍可用

### 2.6 异常是语言机制

- 异常类型可以是任意类型：基础类型、struct、class、指针、用户自定义类型
- 异常不要求继承标准库基类
- `throw` / `catch` / `try` / `throw;` 由编译器和运行时实现
- 异常对象、typeinfo、展开、析构、重新抛出由运行时 ABI 定义
- 没有标准库时，`throw MyError(...)` 仍然合法

### 2.7 `?` 使用语言级协议

`?` 不能硬编码标准库 `Result`。

建议定义语言级协议/概念，例如：

```c^
concept Try<T> {
    ...
}
```

- 内建 `T?` 实现 nullable 传播
- 标准库 `Result<T, E>` 实现 `Try`
- 自定义标准库也可以实现 `Try`
- 没有默认标准库时，自定义 `Result` 仍可使用 `?`

### 2.8 字符串插值使用语言级协议

`$"Hello {name}"`：

- 编译器只负责解析和 lowering
- 实际格式化由语言级插值协议实现
- 默认标准库 `std.text` 提供默认实现
- 自定义标准库可以提供自己的插值实现
- 没有标准库且没有插值实现时，报“缺少插值实现”，而不是编译器内置格式化规则

### 2.9 分配器与运行时钩子

- `new/delete` 默认使用运行时分配器钩子
- hosted 模式默认使用 `malloc/free`
- freestanding 模式允许用户提供分配器
- `panic` / `abort` / `terminate` 使用运行时钩子
- 运行时钩子应由 ABI 文档定义，不依赖标准库类型

### 2.10 hosted / freestanding

- **hosted**：默认标准库 + 平台 libc/OS
- **freestanding**：无默认标准库；语言核心 + 运行时可用；libc/OS 可选
- 异常在 freestanding 下是否可用，取决于运行时是否提供展开实现
- 如果完全没有运行时，异常不可用，这是工具链配置问题，不是语言语义问题

## 3. 备选方案

### 方案 A：异常依赖标准库错误基类

优点：实现简单，统一错误对象。  
缺点：没有标准库就不能抛异常；自定义标准库被绑定。

结论：不选。

### 方案 B：标准库不可替换

优点：编译器可以假设 `std` 存在。  
缺点：用户无法替换标准库，语言核心与标准库耦合。

结论：不选。

### 方案 C：语言核心 + 运行时 + 可替换标准库（推荐）

优点：异常独立、标准库可替换、freestanding 可行。  
缺点：需要明确运行时 ABI 和标准库边界。

结论：选 C。

主要涉及：

行为变化：

- 默认标准库仍然存在，但不再被语言核心硬依赖；
- 异常 payload 和 typeinfo 进入运行时 ABI；
- `?` 不再绑定 `Result`；
- 字符串插值 lowering 到协议；
- 无标准库时，异常、defer、数组、切片仍可用；
- 自定义标准库可以通过 `--stdlib-path` 替换。

## 5. 迁移计划

### Phase 0：冻结边界

- 明确语言核心 / 运行时 / 标准库职责；
- 明确 `--no-stdlib` / `--stdlib-path`；
- 明确异常运行时 ABI；
- 明确 `Try` 协议与插值协议。

### Phase 1：运行时独立

- 引入 `libc_hat_rt`；
- 异常对象、typeinfo、展开、terminate；
- 分配器钩子；
- 无标准库异常测试。

### Phase 2：标准库可替换

- 默认标准库路径；
- `--no-stdlib`；
- `--stdlib-path`；
- 自定义标准库示例；
- 不自动 import 标准库。

### Phase 3：协议化

- `Try` 协议；
- 字符串插值协议；
- 自定义 `Result` 支持 `?`；
- 自定义插值实现。

### Phase 4：freestanding

- 无 libc 配置；
- 用户分配器；
- 运行时最小实现；
- 平台 ABI 测试。

## 7. 验收标准

- 无标准库时，`throw` / `catch` / `try` 可用；
- 无标准库时，`defer` / RAII / 数组 / 切片可用；
- `--no-stdlib` 编译最小异常程序通过；
- `--stdlib-path` 可替换标准库；
- 自定义 `Result` 可通过 `Try` 协议使用 `?`；
- 自定义插值实现可用；
- 默认标准库与运行时边界文档一致；
- hosted / freestanding 行为有测试。
