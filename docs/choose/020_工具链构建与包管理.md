## 1. 背景

C^ 目前主要依赖直接调用编译器：

```bash
./build/src/c_hat_compiler main.ch --run
./build/src/c_hat_compiler main.ch
./build/src/c_hat_compiler main.ch --emit-obj
```

但长期需要：

- 项目级构建
- 模块路径管理
- 依赖管理
- 标准库分发
- 调试信息
- 格式化/LSP
- 跨平台工具链
- 可复现构建

如果工具链设计不先收敛，后续模块/标准库/包管理会反复改。

---

## 2. 决策

### 2.1 v1 工具链范围

v1 稳定范围只包含：

- `chc` 编译器 CLI
- 直接编译单文件/多文件
- `--module-path` / `--stdlib-path`
- `--run` JIT
- `--emit-llvm` / `--emit-obj` / `--emit-asm`
- 基础链接配置
- 标准库随编译器发布

v1 不承诺：

- 完整包管理器
- 依赖解析/版本锁定
- 增量编译缓存
- LSP/格式化器完整实现
- 调试器集成

### 2.2 项目布局

建议项目布局：

```text
project/
  c_hat.toml          # 项目清单（可选，后续）
  src/
    main.ch
    app/
      module.ch
  tests/
  build/
```

- v1 不强制项目清单；可以直接编译 `.ch` 文件。
- 多文件项目通过 `--module-path` 指定搜索路径。
- 标准库通过 `--stdlib-path` 或默认路径。
- 包管理器后续引入 `c_hat.toml`。

### 2.3 构建命令

建议长期提供：

```bash
chc build
chc run
chc test
chc check
chc fmt
chc lsp
```

v1 可以先只保留：

```bash
chc <input.ch> [--run] [--emit-obj] ...
```

后续再引入 `chc build` / `chc test`。

### 2.4 包管理

- v1 不做完整包管理器。
- 后续包管理器需要：
  - 依赖声明
  - 版本解析
  - 锁定文件
  - 本地缓存
  - 源/注册表
  - 可复现构建
- 包管理器不能改变语言语义或 ABI。
- 标准库随编译器发布，不通过包管理器安装。
- 自定义标准库通过 `--stdlib-path` 或包依赖提供。

### 2.5 模块路径与构建

- 模块路径是逻辑路径，不是文件系统硬编码。
- 模块解析顺序：
  1. 项目源目录
  2. `--module-path`
  3. 标准库路径
- 同名模块冲突报错。
- 循环依赖报错。
- 模块编译顺序按依赖关系。
- v1 可以整程序编译；长期支持独立对象文件。

### 2.6 调试信息

- v1 至少生成基础行号信息。
- 长期支持 DWARF（Linux/macOS）和 PDB（Windows）。
- 调试信息不能改变 ABI。
- 优化构建可以剥离调试信息。
- 变量名/类型信息尽可能保留。

### 2.7 可复现构建

- 相同源码、相同工具链、相同目标应产生相同输出。
- mangling、模块路径、类型布局必须确定。
- 禁止随机/时间相关输出影响构建结果。
- `__timestamp__` 等 builtin 需要：
  - 默认不影响可复现构建，或
  - 显式 opt-in，或
  - 在 `--reproducible` 下报错。
- 构建缓存/临时文件名不得影响产物。

### 2.8 跨平台工具链

- Linux/macOS：`.o`，`$CXX`/`c++` 或配置 linker。
- Windows：`.obj`，`lld-link`/`link.exe`。
- 目标三元组（target triple）由编译器配置。
- v1 源码语义跨平台一致；二进制 ABI 完全一致不作为承诺。
- 标准库需要跨平台实现或平台适配层。

### 2.9 工具链与语言核心解耦

- `chc` 编译器不依赖包管理器。
- 包管理器不改变语言语义。
- 格式化器/LSP 只消费 parser/semantic 结果。
- 调试器只消费调试信息。
- 标准库可替换，不绑定工具链。

### 2.10 测试与 CI

- 编译器自身测试：
  - 单元测试
  - 集成测试
  - conformance test
- 语言测试：
  - 正向/负向语义测试
  - ABI 测试
  - 跨平台构建测试
- CI 至少覆盖 Linux；Windows 后续加入。
- 标准库测试独立于编译器测试。

## 3. 备选方案

### 方案 A：v1 直接做完整包管理器

优点：生态完整。  
缺点：过早引入依赖解析/版本/注册表，拖慢核心。

结论：不选。

### 方案 B：v1 只保留编译器 CLI（推荐）

优点：核心优先，工具链后置。  
缺点：项目级体验较弱。

结论：选 B。

### 方案 C：完全依赖外部构建系统

优点：不重复造轮子。  
缺点：语言缺少统一体验，模块/标准库分发困难。

结论：不选。
