## 1. 背景

C^ 已有：

- `module a.b.c;`
- `import a.b.c;`
- `public import`
- `extern "C"` FFI
- 一个最小 `stdlib/std`

但当前：

- import 主要只合并模块符号，未完整导入公开函数；
- codegen 忽略 `ModuleDecl` / `ImportDecl` / `ExportDecl`；
- 没有稳定 mangling；
- 没有独立对象文件模型；
- 标准库只有少量文件；
- Windows/Linux 链接差异未形成正式 ABI 规范。

需要先确定模块与 ABI 模型，否则标准库和 FFI 无法稳定扩展。

---

## 2. 决策

### 2.1 模块是编译单元

- 一个 `.ch` 文件对应一个模块。
- `module a.b.c;` 声明模块路径。
- 模块路径映射到文件路径：`a/b/c.ch` 或 `a/b/c/mod.ch`。
- 模块可以被独立解析、语义分析、生成对象文件。
- v1 可以先做“整程序编译 + 语义导入”，但 ABI 设计按独立对象文件预留。

### 2.2 导入与可见性

- `import a.b.c;` 导入模块的公开符号。
- `public import` 将导入的公开符号继续导出。
- `private` / `internal` 符号不导出。
- 循环导入报错。
- 模块初始化顺序：依赖先于使用者；v1 不引入全局构造器。
- 模块名冲突使用完整路径或显式别名解决。

### 2.3 符号导出与 mangling

- `extern "C"` 使用 C ABI，不 mangle。
- 普通 C^ 符号使用稳定 mangling。
- mangling 必须包含：
  - 模块路径
  - 函数/类/方法名
  - 参数类型
  - 泛型实例化参数
  - 命名空间/类前缀
- v1 的 mangling 规则一旦用于标准库，必须冻结；后续版本只能扩展，不能随意改名。
- 建议格式：
  - 函数：`module.func@type1#type2`
  - 方法：`module.Class_method@...`
  - 泛型实例化：`module.func__int@...`
  - 类：`module.Class`
  - vtable：`module.Class__vtable`

### 2.4 独立编译与链接

长期目标：

- 每个模块生成对象文件；
- 导出符号按 public/internal 可见性生成；
- 导入模块只读取公开声明，不重新生成实现；
- 最终链接器合并对象文件；
- 支持静态库/动态库。

v1 可以：

- 整程序编译；
- 语义层合并 import；
- codegen 生成单模块 IR；
- 但 mangling 和公开符号规则先按独立编译设计。

### 2.5 C ABI / FFI

- `extern "C"` 使用平台 C ABI。
- 基础类型映射：
  - `int` -> `int32_t`
  - `long` -> `int64_t`
  - `float` -> `float`
  - `double` -> `double`
  - `byte` -> `uint8_t`
  - `bool` -> `_Bool`/`bool`（按平台）
  - 指针 -> `void*`/对应指针
- `literalview`/`byte![]` 传 C 字符串时需显式转换/终止符处理。
- 变参 FFI 需要单独支持 `...` 调用约定。
- 函数指针与 C 函数指针互操作需要 ABI 兼容。
- 结构体按值传参与平台 ABI 对齐，v1 可限制为简单布局。

### 2.6 标准库分层

建议标准库按模块分层：

```text
std.core      // 基础类型、Option/Result、断言
std.mem       // 分配、指针、内存操作
std.string    // string（拥有型字符串）
std.text      // 格式化、插值
std.io        // 控制台/文件
std.collections // 容器（后置）
std.math      // 数学
std.test      // 测试
```

- `string` 属于 `std.string`，不是编译器内建类。
- `literalview` 是编译器内建的非拥有视图。
- 字符串插值 lowering 到 `std.text` 的插值 API。
- 标准库先做最小 core/io/mem/string，再扩展容器/网络/并发。

### 2.7 平台差异

- Linux/macOS：`.o`，使用 `$CXX`/`c++` 或配置的 linker。
- Windows：`.obj`，使用 `lld-link`/`link.exe`。
- 目标文件是否 PIC、异常模型、调用约定由平台配置决定。
- v1 不承诺跨平台 ABI 完全一致，但源码语义应一致。

### 2.8 包与构建

- 模块路径是逻辑路径，不是文件系统路径的硬编码。
- 支持 `--module-path` / `--stdlib-path`。
- 后续包管理器负责依赖、版本、构建。
- 标准库随编译器发布，不依赖系统包管理器。

### 2.9 已确认补充决策

1. **v1 实现方式。**
   - v1 可以先整程序编译 + 语义导入。
   - mangling、public 符号、模块路径按独立编译设计。
   - 独立对象文件作为后续实现，不改变 ABI 规则。

2. **mangling 包含模块路径。**
   - 普通 C^ 符号的 mangling 包含模块路径。
   - `extern "C"` 不 mangle。
   - 标准库符号也遵循同一规则。

3. **import 默认导入公开符号。**
   - `import a.b.c;` 导入公开函数/类/类型。
   - `public import` 继续导出。
   - 私有/internal 符号不导入。

4. **`string` 完全移出编译器内建类型。**
   - `literalview` 保留为编译器内建视图。
   - `string` 属于 `std.string`。
   - 编译器不硬编码 `string` 的存储/格式化。

5. **字符串插值 lowering 到标准库协议。**
   - 默认由 `std.text` 实现。
   - 编译器只解析/ lowering。
   - 自定义标准库可实现自己的插值协议。

6. **`delete slice` 为 canonical。**
   - `delete` 接受指针和 owning slice。
   - `delete[]` 作为兼容/底层形式保留。
   - 空指针 delete 为 no-op。

7. **变参 FFI 标记 experimental。**
   - v1 不承诺完整变参 ABI。
   - 基础 `extern "C"` 调用优先。

8. **Windows 是 v1 源码/构建目标。**
   - 源码语义跨平台一致。
   - 二进制 ABI 完全一致不作为 v1 承诺。
   - Windows 需要独立链接/ABI 测试。

9. **标准库随编译器发布。**
   - 默认标准库由编译器提供。
   - 可通过 `--stdlib-path` 替换。
   - 可通过 `--no-stdlib` 禁用。

10. **v1 不引入全局构造器。**
    - 模块初始化顺序按依赖关系。
    - 不执行全局构造器/顶层语句。
    - 静态初始化仅支持常量。

## 6. 开放问题确认结果

1. v1 整程序编译 + 语义导入；ABI 按独立编译设计。
2. mangling 包含模块路径。
3. `import` 默认导入公开符号；`public import` 继续导出。
4. `string` 完全移出编译器内建类型，归 `std.string`。
5. 字符串插值 lowering 到标准库协议，默认 `std.text`。
6. `delete slice` 为 canonical；`delete[]` 兼容保留。
7. 变参 FFI 标记 experimental，不进入 v1 稳定范围。
8. Windows 是 v1 源码/构建目标，二进制 ABI 完全一致不作为承诺。
9. 标准库随编译器发布，可替换、可禁用。
10. v1 不引入全局构造器。
