## 1. 评审目标

C^ 文档同时强调三件事：

- 手动 `new/delete`
- RAII / 自动析构
- `defer` 块级清理
- `late` 延迟初始化
- `~` 移动与所有权
- 异常展开时清理

但当前实现只落地了其中一部分，而且部分语义与设计文档相反。本评审要确定：

1. C^ 的资源管理主模型是什么：RAII、`defer`、还是两者并存？
2. `defer` 是块级还是函数级？
3. 析构函数何时调用？异常路径是否调用？
4. `late` 变量的构造/析构/使用前初始化规则。
5. `new T[n]` / `delete[]` 是否管理元素生命周期？
6. 引用与移动 `~` 在资源模型中扮演什么角色？
7. 异常展开与清理的执行顺序、失败处理。

## 2. 当前实现事实

### 2.1 `defer`

当前行为：

- parser 只接受 `defer expression;`，不接受设计文档中的 `defer { ... }` 块。
- codegen 在函数级收集 `deferExpressions_`，不是块级作用域。
- 每个 defer 有一个运行时 `i1` flag，避免执行未进入分支的 defer。
- `return` / `throw` 时按 LIFO 执行已注册 defer。
- 含 defer 的函数会安装函数级 `setjmp` 清理帧；异常穿过中间函数时执行其 defer。
- 循环内注册的 defer 在函数退出时只执行一次，不是每次迭代一次。
- 同函数 `try` 捕获异常时，defer 可能在 throw 点提前执行。

### 2.2 析构函数

当前行为：

- 显式 `delete obj` 会调用 `ClassName_~ClassName(this)`，然后 `free`。
- 自动析构/RAII 未实现：局部类值、`late` 类对象、数组元素、异常展开都不会自动调用析构函数。
- 栈上类值构造 `ClassName obj(...)` 的端到端支持不完整；当前示例主要使用 `new ClassName(...)`。
- `lateVariables_` 记录初始化状态，但 codegen 中析构调用仍是 TODO。
- 析构函数抛异常的行为未定义。

### 2.3 `new/delete`

当前行为：

- `new T(...)`：`malloc` + 调用构造函数。
- `new T[n]`：`malloc` 连续内存，返回 `{ptr, len}` 切片；**不会逐个调用元素构造函数**。
- `delete p`：显式调用析构函数 + `free`。
- `delete[] slice`：释放底层数组指针；**不会逐个调用元素析构函数**。
- 空指针 delete 未定义/未检查。
- 数组长度没有运行时越界检查。

### 2.4 `late`

当前行为：

- semantic 跟踪 `late` 变量是否初始化，支持 if/try 分支合并。
- codegen 中 `late` 的析构调用未实现。
- `late` 类对象的构造（RVO/原地构造）未完整实现。
- 使用未初始化 `late` 变量时 semantic 有检查，但边界仍需测试。

### 2.5 引用

当前行为：

- 只读引用 `T!&` 的参数传递可用。
- 可变引用 `T&` 的 codegen 不完整：调用点 `&x` 后可能报 `Unknown unary operator` 或崩溃。
- 引用返回、引用局部变量、引用生命周期规则未完整实现。
- 调用点规则：可变引用必须 `f(&x)`；只读引用允许 `f(x)`；指针取地址用 `^x`。
- 引用在 LLVM 层没有独立表示，通常退化为指针。

### 2.6 移动 `~`

当前行为：

- lexer/parser 有 `~` 后缀/移动 token。
- `self~` 未实现。
- 移动语义、所有权转移、调用点 `x~` 的 semantic/codegen 未完整实现。
- 目前资源管理主要依赖显式 `delete` 和 `defer`。

### 2.7 异常展开

当前行为：

- `setjmp/longjmp` 传播异常。
- 含 `defer` 的函数安装清理帧，异常穿过时执行 defer。
- 没有自动析构展开。
- 异常 payload 是 64 位字，结构体按值异常不完整。
- catch 类型精确匹配，不做基类匹配。
- defer 在清理路径上抛异常的行为未定义。

## 3. 设计冲突与风险

### 3.1 `defer` 作用域与文档冲突

文档明确写的是：

> C^ 的 `defer` 是块级作用域（Block Scope）。

当前实现是函数级。这不是小差异：

- 循环内 `defer` 语义完全不同；
- `defer` 与局部对象析构的顺序不同；
- `try/catch` 内 defer 的执行时机不同；
- 文档示例中的 `defer { ... }` 当前无法解析。

### 3.2 RAII 与 `defer` 职责重叠

如果自动析构存在，用户会问：

- 为什么还需要 `defer`？
- 同一个资源同时用析构和 defer 会不会重复释放？
- `defer` 和析构谁先执行？
- 异常路径上两者顺序如何？

必须明确：

- RAII 是默认机制；
- `defer` 是显式清理/补充机制；
- 同一资源不应同时由两者管理；
- 顺序固定并写进规范。

### 3.3 `late` 与自动析构

`late T x;` 的设计价值在于：

- 预留栈空间；
- 条件初始化；
- 只有成功构造才析构；
- 与 RVO/NRVO 配合。

当前 semantic 有初始化跟踪，但 codegen 没有自动析构。没有析构的 `late` 只是一个未初始化变量，无法兑现文档承诺。

### 3.4 引用/移动/所有权没有闭环

当前引用和移动主要停留在语法/局部语义：

- 可变引用 codegen 不完整；
- `~` 没有所有权分析；
- `self~` 未实现；
- 引用返回的生命周期未定义。

如果资源模型选择 RAII，引用和移动必须一起定义，否则无法表达“借用”和“转移”。

### 3.5 异常展开与清理

当前 defer 清理依赖函数级 setjmp 帧。要加入析构，需要明确：

- 当前函数内哪些对象已构造；
- 异常穿过中间函数时，如何逐帧调用析构；
- catch 捕获后，try 内对象是否已析构；
- 析构/defer 自身抛异常是否 terminate；
- 与 `longjmp` 的栈帧失效如何协调。

### 3.6 数组元素生命周期

`new T[n]` 当前只分配原始内存。如果 `T` 有构造函数/析构函数：

- 是否逐个构造？
- 构造失败时已构造元素如何析构？
- `delete[]` 是否逐个析构？
- 切片拷贝/赋值是否复制元素？
- 数组字面量是否调用构造函数？

这些必须与数组/切片值语义一起定。

## 4. 关键决策

### D1：`defer` 的作用域

**方案 A：函数级（Go 风格）**

- 优点：实现简单，与当前代码一致；异常清理帧容易实现。
- 缺点：与现有设计文档冲突；循环内语义不直观；不能替代块级 RAII。

**方案 B：块级（当前设计文档）**

- 优点：符合文档；与局部对象生命周期一致；循环内每次迭代注册一次。
- 缺点：需要作用域栈、块级 cleanup region、异常路径逐层执行；实现成本高。

**推荐：方案 B 作为目标语义。**
如果短期不准备实现块级，应把文档和测试改为函数级，并明确标记为实验性，不能继续宣称块级。

同时需要决定：

- 是否支持 `defer { ... }` 复合语句；
- 循环内 defer 是每次迭代注册一次，还是循环结束只注册一次；
- `break` / `continue` / `return` / `throw` 的 defer 执行边界；
- defer 与析构的先后顺序。

---

### D2：RAII / 自动析构

**方案 A：不做自动析构，只保留显式 delete + defer**

- 优点：实现最小，行为明确。
- 缺点：与 C^ 文档的 RAII 定位冲突；`late` 设计失去核心价值；栈类值没有意义。

**方案 B：只对栈上/late 类值自动析构**

- 优点：兑现 RAII 的核心场景；指针仍显式 delete；与 C++ 风格接近。
- 缺点：需要对象生命周期跟踪、异常展开、移动/拷贝规则。

**方案 C：完整 RAII（栈值、late、数组元素、异常展开）**

- 优点：语言模型统一。
- 缺点：实现量最大，牵涉类型系统、异常、数组、移动。

**推荐：方案 B 作为第一阶段目标，方案 C 作为长期目标。**
先明确“哪些类型有析构、何时调用”，再逐步扩展到数组元素和异常展开。

需要决定：

- 栈上类值是否允许？如何构造/复制/移动？
- 局部变量析构顺序：逆声明顺序？
- 返回值优化/RVO 是否必须？
- 析构函数是否允许抛异常？推荐禁止/terminate。
- 显式 `delete` 与自动析构的边界。

---

### D3：`late` 语义

需要明确：

- `late T x;` 是否要求 `T` 有默认构造函数？
- 第一次赋值是“构造”还是“拷贝赋值”？
- 条件分支中部分初始化如何合并？
- 使用未初始化变量是编译错误还是运行时错误？
- 成功构造后离开作用域/异常展开时是否析构？
- `late` 与 RVO/NRVO 的关系。

**推荐**：

- `late` 只允许有明确构造语义的类型；
- semantic 做控制流初始化检查；
- 未初始化使用是编译错误；
- 成功初始化后按普通局部对象参与析构；
- 初期可以限制 `late` 只支持标量和简单结构，逐步扩展。

---

### D4：`new/delete` 与数组元素生命周期

需要明确：

- `new T` 是否调用构造函数？（当前是）
- `new T[n]` 是否逐个构造元素？
- 构造失败时如何清理已构造元素？
- `delete p` 是否调用析构？（当前是）
- `delete[] slice` 是否逐个析构？
- 空指针 delete 是否安全？
- `new T[n]` 返回切片后，切片的拷贝/赋值是否共享底层数组？
- 数组字面量是否调用构造函数？

**推荐**：

- `new T` 调用构造，`delete` 调用析构；
- `new T[n]` 对非平凡类型逐个构造，失败时逆序析构已构造元素；
- `delete[]` 对非平凡类型逐个析构；
- 平凡类型可优化为 `malloc/free`；
- 空指针 delete 定义为 no-op；
- 切片拷贝是浅拷贝，明确文档化；深拷贝需要显式 API。

---

### D5：引用与移动

需要明确：

- `T&` / `T!&` 的调用点规则是否保持“可变必显式 `&`，只读可隐式”？
- 引用在 ABI 中是否就是指针？
- 引用返回的生命周期规则；
- 引用能否绑定临时值；
- `~` 是类型修饰、调用点修饰，还是所有权转移操作？
- `self~` 的语义；
- 移动后源对象状态（未初始化/可析构/不可使用）；
- 移动与析构、异常安全的关系。

**推荐**：

- 保持 choose/006 的调用点规则；
- 引用 ABI 先固定为指针；
- `~` 只表示所有权转移，不改变底层表示；
- 移动后源对象进入“已移动”状态，禁止使用，析构时按空资源处理；
- 第一阶段只支持显式移动，不做隐式移动优化。

---

### D6：异常展开与清理顺序

需要明确：

- 继续 `setjmp/longjmp`，还是转向零开销表驱动？
- 异常展开时，当前函数内局部对象析构顺序；
- 中间函数帧如何逐层清理；
- catch 捕获后，try 内已构造对象是否已经析构；
- defer 与析构的顺序；
- defer/析构抛异常是否 terminate；
- 异常 payload 对结构体/类值的支持。

**推荐**：

- 短期继续 `setjmp/longjmp`，但清理模型按“逐帧 cleanup”设计，避免以后推倒；
- 明确顺序：当前作用域 defer/析构按 LIFO，然后向外层传播；
- 清理过程中抛异常 -> `terminate`；
- catch 捕获后，try 内对象已按展开规则清理；
- 结构体异常 payload 单独设计，不长期依赖 64 位字。

## 5. 推荐目标模型

建议把 C^ 的资源模型定义为：

1. **默认 RAII**：栈上/late 的非平凡对象在作用域退出时自动析构。
2. **`defer` 是块级显式清理**：用于裸资源、C API、成对操作；与 RAII 并存但职责不同。
3. **指针资源显式管理**：`new/delete` 管理堆对象；`new T[n]` / `delete[]` 管理数组元素生命周期。
4. **异常展开执行清理**：defer + 析构，LIFO；清理异常 terminate。
5. **移动 `~` 表示所有权转移**，不改变底层表示；移动后源对象不可用。
6. **引用是借用**：不拥有资源；生命周期由 semantic/规则约束。

这是一个偏 C++/Rust 混合的模型，但与 C^ 文档中的 RAII + defer + late + `~` 方向一致。

## 6. 分阶段落地建议

### Phase 0：冻结语义与文档

- 明确 `defer` 是块级还是函数级；
- 明确自动析构范围；
- 明确 `late`、引用、移动是否属于 v1；
- 把未实现项从“已支持”文档中移出；
- 增加负向测试，防止错误行为被当成规范。

### Phase 1：块级 defer

- parser 支持 `defer { ... }`；
- codegen 使用作用域栈，而不是函数级 vector；
- 每个作用域注册 cleanup region；
- 循环内 defer 每次迭代注册/执行；
- return/throw/break/continue 按作用域边界执行；
- 保留运行时 flag 防止未执行分支。

### Phase 2：栈上/late 自动析构

- 识别有析构函数的局部对象；
- 记录构造状态；
- 正常作用域退出逆序析构；
- return/throw 路径析构；
- `late` 只在成功构造后析构；
- 加入 RVO/移动的最小规则。

### Phase 3：异常展开整合

- 当前函数 cleanup 执行 defer + 析构；
- 中间函数帧逐层清理；
- catch 捕获后 try 内对象已清理；
- 清理异常 terminate；
- 明确 `setjmp/longjmp` 下的对象状态。

### Phase 4：数组元素生命周期

- `new T[n]` 逐元素构造；
- 构造失败逆序析构；
- `delete[]` 逐元素析构；
- 切片/数组拷贝规则；
- 数组字面量构造规则。

### Phase 5：引用与移动

- 完成可变引用 codegen；
- 引用返回/生命周期检查；
- `~` 移动语义；
- `self~`；
- 移动后源对象状态。

主要涉及：

- `src/parser/Parser.cpp`：`defer {}`、移动/引用语法；
- `src/semantic/SemanticAnalyzer.*`：作用域、构造状态、生命周期、移动检查；
- `src/llvm/LLVMCodeGenerator.*`：作用域 cleanup、析构调用、异常展开、数组元素生命周期；

- `tests/defer/`、`tests/exception/`、`tests/late/`、`tests/reference/`、`tests/new_delete/`；
- `docs/spec/C^ 语言内存管理规范.md`、`docs/spec/C^ 语言错误处理规范.md`、`docs/design/defer设计.md`、`docs/design/构造析构设计.md`、`docs/design/late设计.md`。

行为变化：

- 函数级 defer 的现有代码可能改变执行时机；
- 自动析构会让部分“忘记 delete”的代码不再泄漏；
- 移动后源对象使用会被拒绝；
- 异常展开可能触发析构，改变可观察行为；
- 文档中未实现的 RAII 承诺需要删除或标记 experimental。
