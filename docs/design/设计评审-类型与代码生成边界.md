## 1. 评审目标

本评审不讨论“再加什么语法”，而是先确定一个基础边界：

> **类型检查由 semantic 负责，codegen 只消费已确定的类型，还是允许 codegen 根据 LLVM 值反推类型？**

这个边界决定了后续数组、切片、元组、类、引用、只读、泛型、重载、异常 payload 和 ABI 的实现方式。如果继续让 codegen 猜类型，每修一个特性都会引入新的特例。

本评审希望形成以下结论：

1. 表达式/声明的类型信息存放在哪里。
2. semantic 与 codegen 的职责边界。
3. 类型降低（C^ type -> LLVM type）的唯一入口。
4. 缺失类型时的行为：报错还是回退。
5. 数组/切片/元组/类/引用的 ABI 表示由谁决定。
6. 重载与泛型 mangling 的唯一来源。

## 2. 当前实现事实

### 2.1 三层类型信息

当前代码里同时存在三层类型：

1. **AST 语法类型**：`ast::Type`，如 `ast::PrimitiveType`、`ast::ArrayType`、`ast::SliceType`、`ast::TupleType`。
2. **语义类型**：`types::Type`，由 `SemanticAnalyzer` 使用，用于类型兼容、重载、concept、类字段等。
3. **LLVM 类型**：由 `LLVMCodeGenerator::generateType` 降低得到，用于 IR。

问题在于：**第二层类型没有统一附着到表达式上**。大多数表达式在 codegen 阶段只剩 AST 形状和 LLVM 值，没有“这个表达式已经确定为 `types::Type`”的权威信息。

### 2.2 已经附着到 AST 的部分类型信息

目前只有少量节点保存了语义阶段的结果：

- `MemberExpr::structName`
- `CallExpr::resolvedMangledName`
- `DeleteExpr::typeName`
- `ThrowStmt::exceptionTag`
- `CatchStmt::catchTag`

这些字段都是为解决具体问题逐步加上的，不是统一的类型模型。

### 2.3 codegen 中的类型推断/猜测

当前 codegen 存在多处“根据 AST 形状或 LLVM 值反推类型”的逻辑：

- `generateVariableDecl`：
  - 根据初始化器是字面量、函数调用、标识符、成员、数组字面量、`new` 等分支推断变量类型；
  - 对二元/一元/下标/条件表达式，最近增加了“先生成值，再按值的 LLVM 类型分配变量”的兜底；
  - 仍有 `llvm::Type::getInt32Ty(context())` 默认回退。
- `generateIdentifier`：
  - 从 `namedValues_` 取 alloca/值，再 load；
  - 指针 pointee 类型通过 `namedValuePointeeTypes_` 旁路表补充。
- `generateMemberExpr`：
  - 根据 LLVM 类型判断数组、切片、指针、类、元组；
  - 通过 `structInfo_` / `structTypes_` 猜字段索引。
- `generateSubscriptExpr`：
  - 根据对象 LLVM 类型判断数组、切片、指针、元组；
  - 指针元素类型依赖 `namedValuePointeeTypes_`；
  - 元组下标要求常量。
- `generateType`：
  - 固定数组只支持字面量长度；
  - `isReadonlyType` 直接返回 `false`；
  - `generateTypeExpr` 返回 `nullptr`；
  - 未知类型经常回退到 `int32`。

### 2.4 已经暴露的问题

这些不是假设，而是实现过程中实际出现的：

- `var x = a[0] + a[1]` 中 `a` 是 `double[]` 时，变量一度被推断成 `int`，导致后续 `if (x > 41.0)` 触发 `ICmp` 断言。
- `double` 条件曾经在 `if/while/do-while` 中直接用 `ICmpNE` 比较，后来才加入 `toBoolean` 修复。
- 数组字面量在语义上是 `ArrayType`，运行时却用切片 `{ptr, len}` 表示；固定数组无初始化器时又用 LLVM 数组表示。
- LLVM 15+ opaque pointer 不携带 pointee 类型，codegen 只能靠 `namedValuePointeeTypes_` 旁路表补。
- `readonly` / `T![]` / `T!&` 的只读信息在 semantic 有检查，但 LLVM 类型降低层没有统一表达。
- 重载解析在 semantic 用 mangled name，codegen 仍保留一套按 LLVM 类型拼名字的备用路径。

### 2.5 结论

当前 codegen **同时承担了代码生成和部分类型推断**。这在早期快速推进时有效，但现在已经影响正确性和可维护性。

## 3. 需要评审的决策

### Q1：表达式类型信息放在哪里？

**方案 A：AST 节点直接保存语义类型**

例如给 `Expression` 增加：

```cpp
std::shared_ptr<types::Type> resolvedType;
```

优点：

- 查找直接，codegen 不需要额外上下文；
- 每个节点自带类型，调试方便。

缺点：

- AST 会依赖 `types` 命名空间，语法树与语义模型耦合；
- AST 克隆、泛型替换、缓存需要同步复制类型；
- `types::Type` 是共享指针，AST 生命周期/所有权需要明确。

**方案 B：独立的 SemanticModel / TypeMap**

semantic 阶段建立：

```cpp
class SemanticModel {
  std::unordered_map<const ast::Expression *, std::shared_ptr<types::Type>> exprTypes;
  std::unordered_map<const ast::Declaration *, std::shared_ptr<types::Type>> declTypes;
};
```

codegen 接收 `const SemanticModel &`。

优点：

- AST 保持纯语法；
- 类型信息集中管理，便于 dump/测试；
- 泛型单态化、克隆节点可以通过新表重新绑定；
- 不污染 AST 的序列化/toString。

缺点：

- codegen 必须接收并传递 SemanticModel；
- AST 指针作为 key 时，克隆/移动后需要重新登记；
- 需要保证 semantic 覆盖所有表达式。

**推荐：方案 B**，除非明确希望 AST 自带类型。
理由：当前 AST 已经承担了语法结构、位置、属性等职责，再塞入语义类型会让泛型克隆和 AST 工具更复杂。独立 TypeMap 更符合“parser/semantic/codegen 分层”。

**待确认**：是否接受 codegen 构造函数/入口增加 `SemanticModel` 参数。

---

### Q2：codegen 是否允许类型回退？

当前大量位置使用：

```cpp
varType = llvm::Type::getInt32Ty(context());
```

作为“不知道类型时的默认值”。

**方案 A：保留回退**

优点：短期兼容现有代码。
缺点：错误被隐藏，后续在 IR 层才崩溃，难定位。

**方案 B：缺失类型直接报编译错误**

优点：错误在类型阶段暴露；codegen 可以假设类型完整。
缺点：需要先补齐 semantic 对所有表达式的类型记录。

**推荐：方案 B**。
在迁移期可以临时保留“带 warning 的回退”，但必须逐步清零；最终 `generateType` 和变量类型推断不允许默认 `int32`。

---

### Q3：类型降低的唯一入口

建议明确一个组件/函数族：

```text
types::Type  --TypeLowering-->  llvm::Type
```

要求：

- 所有 C^ 类型 -> LLVM 类型必须经过同一入口；
- 数组、切片、元组、类、引用、只读、可空、函数类型都有明确规则；
- 不允许 codegen 在业务分支里临时拼 `PointerType::getUnqual` 或 `int32` 代替类型；
- 类型缓存以“语义类型”或“结构化类型”为 key，而不是 AST 指针；
- 对不支持的组合明确报错，而不是静默退化。

当前 `generateType` 可以作为迁移起点，但需要拆出纯降低逻辑，避免它同时承担“猜测 + 降低”。

---

### Q4：数组/切片/元组的 ABI 表示

这一项与《设计评审-内存与资源模型》重叠，但类型边界必须先定：

- 固定数组 `int[3]`：LLVM `[3 x i32]` 还是统一 `{ptr, len}`？
- 切片 `int[]`：`{ptr, i32}` 还是 `{ptr, i64}`？
- 数组字面量：默认产生固定数组还是切片？
- 元组：literal struct 还是命名 struct？是否保证跨编译单元稳定？
- 类/结构体：字段布局、继承前缀、空类占位字段。
- 引用 `T&` / `T!&`：LLVM 指针还是其他表示？
- 可空 `T?`：是否使用 tagged union / null 指针？
- 只读 `T!`：是否在 LLVM 层完全擦除，只在 semantic 检查？

**推荐**：

- 语义层保留完整类型（含只读、可空、引用）；
- LLVM 层允许擦除只读，但必须有明确的“擦除规则”和测试；
- 数组/切片/元组表示在评审后冻结，并由 TypeLowering 统一实现；
- 不允许同一语义类型在不同代码路径出现两种 LLVM 表示。

---

### Q5：变量类型与初始化器

当前 `generateVariableDecl` 是类型推断重灾区。建议规则：

- 有显式类型：使用 semantic 给出的类型；
- 无显式类型：使用 semantic 对初始化器表达式记录的类型；
- codegen 不再根据“初始化器是字面量/调用/成员/二元表达式”分支推断；
- 数组/元组/切片字面量的“语法糖类型”由 semantic 决定，不由 codegen 决定；
- `new T[n]` 的返回类型由 semantic 决定（`T[]`），不由 codegen 看 AST 形状决定。

迁移后，`generateVariableDecl` 应主要做：

1. 读取 `declType`；
2. 分配 alloca；
3. 生成初始化值；
4. 做显式允许的转换；
5. store。

---

### Q6：重载与 mangling

当前 semantic 会写 `CallExpr::resolvedMangledName`，但 codegen 仍保留一套按 LLVM 实参类型拼名字的备用路径。

建议：

- 函数调用必须由 semantic 解析出唯一目标；
- codegen 只按 `resolvedMangledName` 查找；
- 删除“按 LLVM 类型拼 mangled name”的备用路径，或只保留给 extern/FFI；
- mangling 规则由 semantic 和 codegen 共享同一个纯函数；
- 泛型单态化后的名字由 semantic 生成，codegen 不再自行推导。

---

### Q7：只读、引用、移动限定符

当前：

- `isReadonlyType` 在 codegen 返回 `false`；
- `generateTypeExpr` 返回 `nullptr`；
- 可变引用 `T&` 的 codegen 仍不完整；
- 移动 `~` 只有 parser token，没有完整 semantic/codegen。

建议在类型评审中明确：

- 只读是否只在 semantic 检查，还是进入 ABI？
- 引用在 LLVM 层是否就是指针？
- 引用返回、引用参数、临时值绑定的生命周期规则；
- `~` 移动是否改变类型，还是只改变调用点/所有权分析；
- `T![]` 与 `T[]` 的 LLVM 表示是否相同。

这些规则不先定，后续资源模型无法实现。

## 4. 推荐架构

建议采用以下分层：

```text
Parser
  -> AST（纯语法 + 位置 + 属性）

SemanticAnalyzer
  -> SemanticModel（表达式类型、声明类型、调用目标、类布局、只读/可空信息）

TypeLowering
  -> LLVM 类型（唯一入口）

LLVMCodeGenerator
  -> 只消费 SemanticModel + AST + TypeLowering，不推断类型
```

### 4.1 SemanticModel 最小内容

建议至少包含：

```cpp
struct SemanticModel {
  std::unordered_map<const ast::Expression *, std::shared_ptr<types::Type>> exprTypes;
  std::unordered_map<const ast::Declaration *, std::shared_ptr<types::Type>> declTypes;
  std::unordered_map<const ast::CallExpr *, std::string> resolvedCalls;
  // 类布局、字段索引、属性、继承信息
};
```

### 4.2 codegen 约束

- `generateExpression` 返回 LLVM 值，但表达式类型从 SemanticModel 读取；
- `generateVariableDecl` 不推断类型；
- `generateMemberExpr` / `generateSubscriptExpr` 不靠 LLVM 值猜数组/切片/元组/类；
- 找不到类型时 `error()`，不默认 `int32`；
- `generateTypeExpr` 要么实现，要么明确删除/报未实现，不返回空指针让上层猜。

### 4.3 调试能力

建议增加：

- `--dump-types`：按 AST 节点输出 semantic 类型；
- `--dump-semantic`：输出声明类型、调用目标、类布局；
- 在 `--verbose` 下输出 TypeLowering 结果；
- 类型一致性断言：codegen 得到的 LLVM 类型与 SemanticModel 降低结果一致。

## 5. 迁移计划

### Phase 0：冻结与记录

- 本评审通过后，先不新增类型语法；
- 在 SemanticAnalyzer 中为每个表达式记录类型；
- 在 codegen 中加断言/日志，不改变行为。

### Phase 1：移除变量类型推断

- `generateVariableDecl` 改为读取 SemanticModel；
- 删除字面量/调用/成员/二元表达式分支的 varType 推断；
- 保留显式类型转换；
- 跑全量测试，修复 semantic 漏记录的地方。

### Phase 2：统一类型降低

- 抽出 TypeLowering；
- 移除 `generateType` 中的 `int32` 默认回退；
- 实现数组/切片/元组/引用/只读/可空的明确规则；
- 统一 slice 类型复用与元素类型记录，删除 `namedValuePointeeTypes_` 这类旁路表。

### Phase 3：ABI 与值语义

- 冻结数组/切片/元组/类的 LLVM 表示；
- 处理函数参数/返回值 ABI；
- 处理泛型单态化后的类型一致性。

### Phase 4：只读/引用/移动

- 明确只读擦除规则；
- 完成可变引用 codegen；
- 定义 `~` 移动语义与类型关系。

## 6. 对现有代码的影响

主要涉及：

- `src/ast/`：是否需要 `resolvedType`（推荐不直接加）；
- `src/semantic/SemanticAnalyzer.*`：记录所有表达式/声明类型；
- `src/llvm/LLVMCodeGenerator.*`：接收 SemanticModel，移除推断与回退；
- `src/types/`：类型降低规则、只读/引用/可空；
- `tests/integration/`：新增类型一致性端到端测试；
- `docs/spec/C^ 语言实现现状与语法速查.md`：更新功能状态。

行为变化：

- 一些目前“靠 codegen 猜对”的代码会被拒绝，这是预期；
- 一些目前能通过但类型不一致的代码会暴露为 semantic 错误；
- `int32` 回退删除后，未实现的类型会明确报错。

## 7. 待评审确认的问题

1. 表达式类型信息采用 AST 字段还是独立 SemanticModel？
2. codegen 是否允许任何形式的类型回退？
3. 数组字面量默认是固定数组还是切片？
4. 只读类型是否在 LLVM 层完全擦除？
5. 引用在 LLVM 层是否固定为指针？
6. 函数 mangling 是否完全由 semantic 决定？
7. 是否接受“未实现类型直接报错”的兼容性代价？
8. 是否先做 Phase 1（移除变量推断），还是直接做完整 TypeLowering？

## 8. 验收标准

- 所有 `ast::Expression` 在 semantic 后都有类型记录；
- `generateVariableDecl` 不再有初始化器形状推断；
- `generateType` 不再对未知类型返回 `int32`；
- `generateMemberExpr` / `generateSubscriptExpr` 不再依赖 LLVM 值猜类型；
- 函数调用只使用 semantic 解析结果；
- 新增类型一致性测试：
  - double 表达式变量
  - 数组/切片/元组/类字段
  - 指针/引用/只读
  - 泛型单态化
  - 重载调用
- `--dump-types` 能输出与 codegen 一致的类型；
- 文档中的类型状态与实现一致。
